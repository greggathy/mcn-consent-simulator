Externally mastered consent for Marketing Cloud Next (Snowflake in this POC) · POC results, updated 2026-10-01

MC Next Consent Simulator

An external system of record can be the consent master for MC Next. This POC used Snowflake, but the same pattern works with any external system. Changes in either system reach the other within about 15 minutes, and MC Next only emails people Snowflake (or an MC Next unsubscribe) says are opted in.

What we proved

  1. Opt-ins from Snowflake lead to real emails. The sync pushes them and the send goes. Scenario 1
  2. Upper or lower case in an address doesn't matter at send time. Scenario 11
  3. An Unsubscribe click reaches Snowflake in about 90 seconds, and the sync never undoes it by itself. Scenario 2
  4. Re-subscribing works. A newer Snowflake opt-in turns an opt-out back on. Scenario 9
  5. Email address changes are fixable. Consent doesn't follow a person to a new address, but pushing consent for the new address restores sends. Scenario 4
  6. Two people sharing one address get two emails, one each, and one opt-out stops both. Scenario 5

Decision 2026-10-01

Snowflake is the master and may re-subscribe people, including someone who clicked Unsubscribe in an MC Next email. Whoever writes that opt-in into Snowflake owns having a lawful reason for it.

Also shown: consent mapped straight into Data 360 is ignored at send time (Scenario 8), and someone with no consent record is never emailed (Scenario 7).

Parked: one person with two addresses (Scenario 6), and a late opt-out dated before the last push, which the sync skips (Scenario 10). That one is worth knowing about but isn't breaking. A fix is documented: when Snowflake says opted out and MC Next says opted in, always push the opt-out.

POC closed 2026-10-01. The sync and the return path are left running, but the Snowflake import now runs hourly to save trial credits, so an MC Next opt-out can take up to about an hour to reach Snowflake. Tested timings above used a manually triggered import.

How a send decides

Consent key

In MC Next, consent belongs to the email address and the subscription channel.

MC Next consent stores no link to the person.

KB 005389883 · tested 2026-08-18 (Q4 test, test #7)

PartyId

PartyId is required on contact points, and blank on consent.

On Contact Point Email and Phone, PartyId links a person (GUID) to an address. Without it, people can't be segmented or emailed: Snowflake contacts only reached a send after PartyId was added (2026-09-24).

On consent rows, PartyId is always empty by design. You don't need to set it there.

KB 005389883, KB 005389884 · tested 2026-08-18: 0 of 24 consent rows had a PartyId · tested 2026-09-25: contacts with PartyId unified and were segmented

At send time

person→ address List 1→ permission List 2

A segment picks people. List 1 gives each person's address. List 2 gives that address's permission.

KB 005389883 · tested 2026-09-25 and 2026-09-28

Only consent written through a supported path counts at send time: Create Consent, CSV import, unsubscribe links, preference pages or the Consent Status component. Rows mapped in from a data stream look saved but are ignored (KB 005316463, Scenario 8).

PartyId links people to addresses, so set it on every contact point. Consent links addresses to permission. MC Next never links people to permission directly.

            Background and references

            How GUID and PartyId fit the consent model, a glossary, and every source used.

            Where GUID goes

            GUID maps to the Individual Id and to PartyId on Contact Point Email and Contact Point Phone. It never maps to consent.

            This POC used a GUID, but it could be any External Customer ID the source system owns.

            • GUIDIndividual Idmaps
            • GUIDContact Point Email · PartyIdsource rows (List 1)maps
            • GUIDContact Point Phone · PartyIdsource rowsmaps
            • GUIDUnified Individualthrough the identity link; unified rows carry the Unified Individual Id as PartyIdobserved
            • GUIDCommunication Subscription Consent · PartyIdblank by designnever

            KB 005389883 describes MC Next consent as “intentionally agnostic of PartyID”. Consent is keyed on the contact point value plus the CSCT Id, and it stores no link to the Individual or Unified Individual. The KB gives two reasons:

            • It avoids conflicting consents when several people share an address.
            • It is the conservative default regulators expect, because enforcement is against the address being messaged.

            The segment has to supply the person-to-address link upstream, through List 1. To connect consent rows to a person, join the contact point value to Contact Point Email or Phone, which carry PartyId (KB 005389884).

            Tested in 260715SDO

            • 2026-08-180 of 24 consent rows org-wide had a PartyId. After a real Contact was created and unified through Identity Resolution, the consent rows still had no PartyId.
            • 2026-09-25Snowflake contact points were missing PartyId until 2026-09-24. After it was added, Snowflake-only people unified, could be segmented and reached the send step. On 2026-09-30 a Snowflake-only person was SENT for the first time.

            Checked in 260715SDO

            • 2026-09-30The org's own mapping from MC Next's consent store into the consent data model object includes a PartyId field mapping. The source field is always empty.

            Observed in 260715SDO

            • 2026-09-30After Identity Resolution, the unified copy of List 1 (Unified Contact Point Email) has its PartyId set to the Unified Individual's own Id, a system-generated hash. The GUID stays on the source contact point rows, and the identity link maps the GUID to the unified person.
            • 2026-09-30The org's Identity Resolution match rule merges source profiles only when the first name matches (fuzzy), the last name matches exactly, and the normalised email matches. For example, three source people with the same name and the same address became one Unified Individual. So two GUIDs sharing an address merge only if their names also match. Different-named people who share an address stay separate people, and they share one consent record (Scenario 5).

            Also documented

            • Segmenting directly on consent isn't supported out of the box. The documented workaround is a Calculated Insight, which is metered Data 360 usage (KB 005389883).
            • PartyId is written blank on consent audit rows by design, even when the upstream record is a Lead or Contact (KB 005389884).
            • Status values must be exactly OPT_IN or OPT_OUT. Values such as OptIn cause rejected rows. The Create Consent action produces the correct values (KB 005389884).

            Why does consent have a PartyId field if it's always blank?

            It's a shared, standard object

            Communication Subscription Consent is a standard data model object, used by more than MC Next.

            Sources: Communication Subscription Consent DMO. The related Engagement Channel Type Consent DMO defines its PartyId as a foreign key to Individual.

            Other sources can fill it in

            For example, the core CRM consent objects, brought in through their own data stream, can populate it.

            Sources: Communication Subscription Objects; Create a Data Stream for the Communication Subscription Consent Object.

            Salesforce may use it later

            Inference: two roadmap items in the KBs (per-person consent history, subscriber-key consent segmentation) would need a person link. No committed dates.

            Even if it were filled in, sends would still only check address + subscription channel.

            Glossary
            GUID
            The person ID this setup puts on source records. This POC used a GUID, but it could be any External Customer ID the source system owns. It maps to the Individual Id and to PartyId on Contact Point Email and Contact Point Phone. The identity link maps it to the Unified Individual. It never goes on consent.
            Contact Point
            A record that links an email address (Contact Point Email) or a phone number (Contact Point Phone) to a person through its PartyId. List 1 on this page.
            Unified Individual
            The merged person that Identity Resolution builds from source profiles. Its Id is system-generated, and the unified contact point rows carry it as their PartyId. It can have several contact points.
            Communication Subscription
            The subscription a consent record covers, for example Marketing. A send checks consent for the subscription it uses.
            CSCT
            Communication Subscription Channel Type = one subscription × one channel, for example Marketing × Email. Consent is keyed on the contact point value plus the CSCT Id.
            Create Consent action
            The flow element that writes consent through MC Next's own path. Its four inputs are consent status, contact point, channel and communication subscription. The address must come through the flow's contact-point merge field. In this POC it runs inside the On-Demand Flow (see Flows used).
            Flows used
            Two types. An On-Demand Flow is the write path: a scheduled Apex job calls it over REST every 15 minutes, and it runs the Create Consent action. MC Next campaign flows (segment-triggered, run once on activation) did the test sends, and consent is checked at send time. Salesforce also supports Create Consent in event-triggered and Data Cloud-triggered flows. This POC didn't use them.
            Audit trail
            An append-only record of every consent change. It stores the write time and the capture time supplied by the caller. The Create Consent action sets that capture time to the write time (observed 2026-09-28). PartyId on its rows is blank by design.
